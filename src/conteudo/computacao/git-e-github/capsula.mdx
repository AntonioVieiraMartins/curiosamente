## As primeiras ferramentas

O **SCCS** começou em 1972 (o manual é de dezembro de 1975). O **RCS** veio em 1982. O **CVS** acrescentou a esses sistemas a capacidade de várias pessoas trabalharem ao mesmo tempo, em rede. O **Subversion** (2000) virou o sucessor do CVS. Todos eram **centralizados**: havia um único repositório "oficial" num servidor, e quem queria mexer pegava os arquivos de lá.

## O estalo de Linus Torvalds

Desde 2002, o desenvolvimento do **núcleo do Linux** usava o BitKeeper, um programa proprietário. Em 2005, a licença gratuita do BitKeeper foi revogada. **Linus Torvalds**, criador do Linux, não achou nenhum sistema livre que servisse, então escreveu o seu. Começou em **3 de abril de 2005**, anunciou em 6 de abril e, **no dia seguinte**, o Git já guardava o próprio código-fonte. Em 16 de junho de 2005, o Git gerenciou o lançamento do Linux 2.6.12. Torvalds passou a manutenção a Junio Hamano em 26 de julho, e a versão 1.0 saiu em 21 de dezembro de 2005.

O nome? Torvalds brincou que dá nome aos projetos a partir de si mesmo: "primeiro Linux, agora git". A palavra também é uma gíria britânica para uma pessoa desagradável. O manual do programa o chama de "o estúpido rastreador de conteúdo".

## O GitHub: um lugar para o Git

Desenvolver o Git era uma coisa. Colaborar com ele era outra: era preciso um servidor, contas, permissões. Em 19 de outubro de 2007 começou o desenvolvimento do **GitHub**, fundado por Tom Preston-Werner, Chris Wanstrath, P. J. Hyett e Scott Chacon. O site abriu em **10 de abril de 2008**. Em 2009 tinha cerca de 100 mil usuários. Em janeiro de 2023, mais de 100 milhões de pessoas desenvolvedoras e mais de 420 milhões de repositórios. Em **4 de junho de 2018**, a Microsoft anunciou a compra do GitHub por **7,5 bilhões de dólares** (negócio fechado em 26 de outubro de 2018).

## 1. Git é "salvar o jogo"

Num videogame, você salva o jogo em vários pontos. Se der errado, volta a um ponto anterior. O Git faz o mesmo com um **projeto inteiro**:

- Cada **commit** é um ponto de salvamento: uma "foto" de todos os arquivos naquele momento, com **autor**, **data** e uma **mensagem** que explica o que mudou e por quê.
- O conjunto de commits é o **histórico**. Com ele, dá para ver versões antigas, comparar e **voltar**.
- A pasta com o projeto e todo o seu histórico se chama **repositório**.

O controle de versões traz outros benefícios: **responsabilidade** (registros de quem mudou o quê, quando e por quê), **depuração** (testar versões antigas para achar quando um defeito entrou) e **colaboração** (mensagens de commit melhoram a comunicação).

## 2. Git guarda fotos, não só diferenças

O Git armazena **instantâneos** (*snapshots*) de toda a árvore de arquivos, e não apenas a lista de mudanças de cada arquivo. Um commit registra uma árvore, um horário, uma mensagem e o(s) commit(s) **pai(s)**: aquele que veio antes. Por isso o histórico é uma **corrente**: cada commit aponta para o anterior.

## 3. Distribuído: todo mundo tem uma cópia completa

Os sistemas antigos eram **centralizados**: um servidor, e todo mundo dependia dele. O Git é **distribuído**: cada pessoa tem **o repositório inteiro**, com todo o histórico, no próprio computador. Isso significa que o trabalho **não exige rede nem servidor central**, que fazer commits, ver o histórico e voltar atrás é rápido, e que cada cópia funciona também como **backup**. Equipes costumam usar um servidor central (como o GitHub) como cópia compartilhada, por conveniência.

## As três áreas: mesa, bandeja e histórico

O Git não salva tudo automaticamente. Você **escolhe** o que entra em cada commit. Para isso, existem três áreas:

- A **mesa de trabalho** (diretório de trabalho): onde você edita os arquivos.
- A **bandeja** (o *index*, ou área de preparação, em inglês *staging area*): o que você **separou** para o próximo commit. O index é a área entre o diretório de trabalho e o banco de objetos, que guarda as mudanças na fila do próximo commit.
- O **histórico**: os commits já feitos.

Os comandos que levam de uma área à outra :

- `git init`: cria um repositório novo.
- `git add [arquivo]`: coloca a mudança na bandeja.
- `git commit -m [mensagem]`: salva a bandeja como um novo commit.
- `git clone [endereço]`: cria uma cópia de um repositório que já existe em outro lugar.

<Aprofundar titulo="Por que existe a bandeja">
Parece um passo a mais, mas a bandeja deixa **montar commits com sentido**. Suponha que você mexeu no botão e também, sem querer, numa configuração de teste. Com a bandeja, você faz `add` só do botão e dá um commit com a mensagem "corrige o botão". A configuração fica de fora, para ser tratada à parte. Um bom commit conta **uma história só**, e a mensagem explica o **porquê** da mudança, e isso vale para todas as mensagens de commit.
</Aprofundar>

## O código de cada commit

Cada objeto do Git é identificado por um **código** calculado a partir do conteúdo, um **hash** (como o que você conheceu na cápsula de senhas). Esses códigos eram calculados com o **SHA-1**. Como o código de cada commit depende do conteúdo **e do commit anterior**, mudar algo no passado muda o código dele e de **todos os que vieram depois**. Por isso adulterações antigas ficam **detectáveis**.

<CorrenteDeCommits />

<Brincando titulo="O código do commit: uma corrente de lacres">

Imagine uma **corrente de lacres**: cada lacre tem uma impressão que depende **do lacre anterior**. Se alguém trocar um elo no meio, a impressão dele muda, e todas as seguintes deixam de bater.

No Git, cada commit tem um código que depende do conteúdo **e do commit anterior**. Isso garante que o histórico não foi alterado escondido: se qualquer coisa mudar, os códigos seguintes mudam também.

Por isso o código do commit funciona como uma **impressão digital** do histórico até ali.

</Brincando>

<ExemploResolvido titulo="Uma corrente de códigos">
  <Passo>O código do commit 1 depende do conteúdo dele.</Passo>
  <Passo>O código do commit 2 depende do conteúdo dele **e do código do commit 1**.</Passo>
  <Passo>Se alguém muda o commit 1, o código dele muda; logo, o do commit 2 também, e o do 3, e o do 4.</Passo>
  <Passo>Quem comparar os códigos com uma cópia boa vê na hora que **algo foi adulterado**.</Passo>
</ExemploResolvido>

<Aprofundar titulo="SHA-1 e a mudança de hash">

Depois dessa demonstração o Git passou a usar uma **variante do SHA-1 resistente àquele ataque**, e desde 2020 existe um **plano de transição de hash** em andamento. O Git foi projetado com salvaguardas fortes contra corrupção acidental ou maliciosa, e a ideia de que o histórico "se prova sozinho" é uma das razões da confiança nele.
</Aprofundar>

## Ramos: experimentar sem medo

Imagine um jogo em que você quer testar uma estratégia arriscada. Em vez de arriscar o seu único salvamento, você **copia** a situação e experimenta nessa cópia. Se der certo, você junta. Se der errado, joga fora.

Isso é um **ramo** (*branch*). Equipes usam ramos para tudo: uma funcionalidade nova, uma correção, uma experiência. Cada pessoa trabalha no seu ramo, e o trabalho é **juntado** (*merge*) no ramo principal quando está pronto. O histórico forma, na prática, um grafo de commits; "uma árvore com junções" é uma boa aproximação.

<Brincando titulo="Ramos: cada pessoa trabalha na sua cópia">

Dois colegas precisam editar o mesmo trabalho. Em vez de brigar pelo mesmo caderno, cada um tira uma **cópia** e escreve na sua. Depois eles **juntam** as duas.

Um **ramo** do Git é essa cópia: dá para experimentar à vontade, sem risco de estragar o caderno principal. Se der certo, junta-se ao principal. Se não, joga-se a cópia fora.

Por isso o Git incentiva criar ramos: experimentar não custa nada.

</Brincando>

<Brincando titulo="Conflito: duas pessoas mexeram na mesma frase">

Dois colegas, cada um na sua cópia, reescreveram **a mesma frase** do trabalho de jeitos diferentes. Na hora de juntar, o Git não sabe qual versão manter, e pergunta.

Isso é o **conflito**. O Git marca os dois trechos, e quem junta **escolhe**: fica com uma, com a outra ou combina as duas.

Se eles tivessem mexido em frases **diferentes**, o Git juntaria sozinho. Só há conflito quando dá para duvidar.

</Brincando>

<ExemploResolvido titulo="Quando há conflito">
  <Passo>O arquivo tem 3 linhas: título, introdução e rodapé.</Passo>
  <Passo>No ramo principal, Bruno muda o **título** para "Novidades".</Passo>
  <Passo>No ramo `nova-ideia`, Ana também muda o **título**, para "Em breve".</Passo>
  <Passo>Ao juntar, o Git vê **dois textos diferentes na mesma linha** e não sabe qual vale. É um **conflito**: alguém escolhe um dos textos ou combina os dois, e então faz o commit da solução.</Passo>
</ExemploResolvido>

<Aprofundar titulo="Por que conflitos são normais">
Juntar (*merge*) é uma das partes **mais complexas** do controle de versões, especialmente para arquivos que não são texto. O merge automático funciona melhor com texto simples. Alguns sistemas antigos evitavam conflitos **trancando** o arquivo (só uma pessoa edita por vez), mas as trancas podem ser esquecidas e dar pressão para driblar o sistema. A abordagem do Git é deixar todo mundo trabalhar livremente e **resolver os conflitos depois**, porque, na prática, eles são raros e pequenos quando as mudanças são feitas em pedaços pequenos e juntadas com frequência.
</Aprofundar>

## GitHub: onde o Git encontra a equipe

**Git** e **GitHub** não são a mesma coisa. O **Git** é o programa que **controla as versões**, escrito por Torvalds, e funciona no seu computador, até sem internet. O **GitHub** é um **site** construído sobre o Git: ele guarda uma cópia do repositório na internet e acrescenta o que falta para trabalhar em equipe: **controle de acesso**, **acompanhamento de defeitos** (as *issues*), **gestão de tarefas** e outras ferramentas.

Outros serviços fazem o mesmo papel: **GitLab**, **Bitbucket** e **SourceForge**. Depois da compra pela Microsoft, esses serviços relataram aumento de usuários que migravam projetos do GitHub.

Dois conceitos do GitHub:

- **Fork:** uma **cópia pessoal** de um repositório de outra pessoa, para você mexer à vontade.
- **Pull request:** um **pedido** para juntar as suas mudanças ao projeto original. Quem mantém o projeto vê as diferenças, comenta e aprova.

Para levar o seu trabalho até lá e de lá:

- `git push`: **envia** os seus commits para o GitHub.
- `git pull`: **traz** os commits novos que outras pessoas enviaram.

<Brincando titulo="Push recusado: o colega salvou antes de você">

Se ele aceitasse, as mudanças do colega seriam **perdidas** por cima. Por isso a regra é: **primeiro baixe** o que há de novo (pull), junte com o seu trabalho e só depois envie.

A recusa não é erro seu, é uma proteção para ninguém apagar o trabalho de ninguém.

## Os comandos, em ordem

Um fluxo típico, do começo ao fim:

- `git clone [endereço]`: traz uma cópia do projeto.
- (você edita arquivos)
- `git add [arquivo]`: separa o que vai no commit.
- `git commit -m "mensagem"`: salva o ponto.
- `git push`: envia ao GitHub.
- `git pull`: traz o que a equipe enviou, de tempos em tempos.

Para começar um projeto **do zero**, o primeiro passo é `git init`. Por tradição, o ramo inicial se chamava `master` e hoje muitos projetos (como este) usam o nome `main`.

<QualComandoGit />

<Aprofundar titulo="Commits enviados não são sobrescritos, e sim revertidos">
No Git, commits que já foram **enviados** a outras pessoas normalmente não se apagam: eles são **revertidos**, ou seja, cria-se um **novo commit** que desfaz o efeito do antigo. Isso mantém o histórico honesto e evita bagunçar o trabalho de quem já baixou aquela versão. A ferramenta `git bisect`, também útil, usa **busca binária** (dividir pela metade) no histórico para achar **qual commit introduziu um defeito**: com 1.000 commits, bastam cerca de 10 testes, a mesma lógica dos índices de banco de dados.
</Aprofundar>

## Boas práticas de quem usa Git

- **Commits pequenos e frequentes**, com mensagens que explicam o **porquê**.
- **Nunca** coloque senhas, chaves ou segredos no repositório: **o que entra no histórico fica no histórico**, mesmo que você apague depois. Este projeto, por exemplo, mantém o arquivo `.env.local` fora do Git.
- Use **ramos** para experimentar e **pull requests** para revisar.
- **Puxe** (`git pull`) antes de começar o dia, para evitar conflitos grandes.
- Dê `git push` com frequência: a cópia no GitHub também é um **backup**.

<Resumo>

- **Git** é "salvar o jogo" do código: cada **commit** é uma foto do projeto, com autor, data e mensagem.
- O Git é **distribuído**: cada pessoa tem o histórico completo, e o trabalho local não exige rede.
- Três áreas: **mesa** (edita), **bandeja** (`git add`) e **histórico** (`git commit`).
- **Ramos** permitem experimentar; **merge** junta. O conflito só acontece no **mesmo trecho**.
- O código de cada commit depende do anterior, então adulterações ficam **detectáveis**.
- **GitHub** é um serviço sobre o Git: guarda a cópia na internet, com forks, pull requests e issues. `git push` envia e `git pull` traz.
- **Nunca** coloque segredos no repositório.

**Um pouco de história.** O SCCS (1972) e o RCS (1982) abriram o caminho do controle de versões, e o CVS e o Subversion (2000) usavam um servidor central. Em abril de 2005, depois do fim da licença gratuita do BitKeeper, Linus Torvalds começou o Git, que em poucos dias já guardava o próprio código. O GitHub abriu em abril de 2008 e foi comprado pela Microsoft em 2018, por 7,5 bilhões de dólares.

</Resumo>
