## As primeiras "APIs": bibliotecas de sub-rotinas

Nos anos 1940, programar o EDSAC era trabalhoso. Wilkes e Wheeler organizaram uma **biblioteca** de pedaços de programa reutilizáveis e um catálogo que dizia o que cada um fazia. Quem usava a biblioteca não precisava saber **como** ela funcionava por dentro, só **como chamá-la**. Essa é a essência de uma API.

A expressão "application program interface" apareceu em 1968, num artigo sobre gráficos remotos, e foi levada para os bancos de dados por C. J. Date em 1974. Hoje a sigla significa "interface de programação de aplicações", e o importante é que ela é uma **interface para programas**, e não para pessoas.

## A virada da Web

Por muito tempo, APIs eram bibliotecas **dentro** do mesmo computador. Em 2000, Roy Fielding descreveu em sua tese um estilo de organizar sistemas que conversam pela rede, o **REST**, e contrastou as APIs "baseadas na rede" com as "baseadas em bibliotecas". Fielding também ajudou a criar as versões 1.0 e 1.1 do HTTP e o padrão de endereços (URI). A partir de cerca de 2000, APIs web em XML e depois em JSON se espalharam.

## O JSON: um formato leve nascido de uma mensagem

Em março de 2001, Douglas Crockford ajudou a fundar uma empresa, a State Software, onde surgiu a sigla **JSON** (*JavaScript Object Notation*, "notação de objetos do JavaScript"). Em abril de 2001, ele e Chip Morningstar enviaram a primeira mensagem JSON. O site json.org foi lançado no mesmo ano. O formato ganhou seu primeiro padrão em outubro de 2013 (ECMA-404) e o padrão de internet atual em dezembro de 2017 (RFC 8259). Hoje é usado muito além do JavaScript, e a extensão de arquivo é **.json**.

## 1. A API como cardápio

Voltando ao restaurante da cápsula anterior: o **cardápio** diz o que dá para pedir (pratos), como pedir (o nome do prato) e o que você recebe (a descrição). Você **não** vê a cozinha, e a cozinha pode mudar a receita por dentro sem você notar, desde que o cardápio continue valendo.

Uma **API** faz o mesmo para programas. Ela é uma interface que permite que programas conversem entre si, definida por uma **especificação** (a lista de chamadas possíveis). Uma boa API mostra só o que quem a usa precisa e **esconde os detalhes internos**. Ela também é comparada a **peças de Lego**: serviços diferentes se encaixam por suas APIs para formar produtos novos.

## 2. A API como contrato

Quem cria a API **promete** que os pedidos funcionarão de certo jeito. Quem a usa **confia** nisso. A API funciona como um **contrato** entre quem fornece e quem depende. Por isso uma API estável dá confiança, e mudar a API de forma abrupta pode **quebrar** quem a usa. (Veja a simulação mais adiante.)

## JSON: o formato da resposta

**JSON** é um jeito de escrever dados como **texto**, de modo que qualquer linguagem de programação consiga ler. É leve (uma alternativa de menor custo ao XML) e legível por pessoas.

Os **tipos de dados** do JSON são só seis:

- **Objeto**: pares `nome: valor` entre chaves.
- **Lista (array)**: valores em ordem, entre colchetes.
- **Texto (string)**: entre **aspas duplas**.
- **Número**.
- **Booleano**: `true` ou `false`, sem aspas.
- **Nulo**: `null`, que significa "sem valor".

<TiposDeJson />

<Brincando titulo="JSON: uma ficha de cadastro">

Pense numa **ficha de cadastro** de papel, com campos e respostas: "nome: Ana", "idade: 30", "estuda: sim". O JSON é essa ficha escrita em texto, para que dois programas se entendam.

Cada linha tem um **rótulo** (a chave, como "nome") e uma **resposta** (o valor, como "Ana"). Uma ficha dentro de outra, como o endereço dentro do cadastro, vira um JSON dentro de outro. E uma **lista** de fichas vira uma lista de JSONs.

Ler um JSON é só ler a ficha: procurar o rótulo e olhar a resposta ao lado.

</Brincando>

<ExemploResolvido titulo="Lendo um JSON">
  <Passo>Veja `{ "nome": "Ana", "idade": 30, "notas": [4, 8, 15] }`.</Passo>
  <Passo>É um **objeto** (entre chaves) com 3 pares: `nome`, `idade` e `notas`.</Passo>
  <Passo>`nome` é texto, `idade` é número e `notas` é uma lista de 3 números.</Passo>
  <Passo>O valor de `idade` é **30**.</Passo>
</ExemploResolvido>

<Brincando titulo="Posição zero: a régua começa no zero">

Olhe uma **régua**: a primeira marca é o **0**, e não o 1. O número da marca diz **quanto você andou** desde o começo, e no começo você andou zero.

Numa lista, a posição também conta **quantos passos** o item está do início. O primeiro item está a zero passos, o segundo a um passo, e assim por diante.

Por isso o "item de posição 0" é o primeiro. Parece estranho, mas é só trocar "ordem" por "distância".

</Brincando>

<Aprofundar titulo="Por que as posições começam em 0">
Em muitas linguagens, a posição de um item numa lista é a **distância** a partir do começo. O primeiro item está a **0** passos do começo, o segundo a **1** passo, e assim por diante. É por isso que, numa lista de 3 itens, as posições são 0, 1 e 2, e não 1, 2 e 3. Parece estranho no início, mas é a convenção da maioria das linguagens de programação, e vale também no JavaScript, onde o JSON nasceu.
</Aprofundar>

## As regras do JSON são rígidas

O JSON é **exigente**. As regras:

- Textos usam **aspas duplas** (aspas simples não valem).
- **Não há comentários.** Crockford os removeu porque as pessoas usavam comentários para dar instruções ao leitor, o que prejudicava a compatibilidade.
- **Vírgula sobrando** no fim de uma lista ou objeto não é permitida.
- Os nomes (chaves) também ficam entre aspas duplas.
- O texto trocado entre sistemas deve usar a codificação UTF-8.

Por que tanta rigidez? Porque o JSON é lido por **programas**, e um programa não "entende o que você quis dizer": se há uma vírgula a mais, ele recusa tudo.

<ExemploResolvido titulo="Achando o erro">
  <Passo>Texto: `{ "nome": "Ana", "idade": 30, }`.</Passo>
  <Passo>Aspas duplas? Sim. Chaves entre aspas? Sim.</Passo>
  <Passo>Mas há uma vírgula depois de `30`, e nada vem depois dela.</Passo>
  <Passo>Esse é o erro da **vírgula pendurada**. O JSON é **inválido**.</Passo>
</ExemploResolvido>

## Escrevendo JSON: dados viram texto

Quando o servidor vai responder, ele pega os dados que tem (na memória, na forma de objetos da linguagem) e os transforma em **texto JSON**. Quando o navegador recebe, faz o caminho inverso: lê o texto e recria os objetos. Preencha os campos e veja o JSON nascer:

<JsonAoVivo />

Repare que o nome vira texto com aspas, a idade vira número sem aspas e a conta ativa vira `true` ou `false`. O JSON é só **texto**, e é exatamente isso que viaja pela rede no corpo de uma resposta HTTP.

<Aprofundar titulo="JSON e XML: dois jeitos de escrever dados">
Antes do JSON, o formato mais comum era o **XML**. O JSON é visto como uma alternativa de menor "sobrecarga" (menos texto para dizer a mesma coisa). O XML permite comentários e separa dados de metadados com elementos e atributos; o JSON não tem essa distinção. O XML tem tipagem forte por esquemas, enquanto o JSON tem seus próprios tipos embutidos e um padrão próprio de esquema, o **JSON Schema**.

O tipo de mídia do JSON na internet é `application/json`, o que aparece nos cabeçalhos HTTP para o navegador saber que o corpo da resposta é JSON.
</Aprofundar>

## REST: endereços que são coisas, métodos que são ações

Em 2000, Roy Fielding descreveu o **REST** na sua tese. Em vez de criar um endereço para cada ação ("/apagarPedido", "/criarPedido"), o REST sugere que o endereço identifique **uma coisa** (um **recurso**, como `/pedidos` ou `/pedidos/7`) e que o **método HTTP** diga o que fazer com ela.

<MontarPedidoRest />

As **restrições** do estilo REST. As principais:

- **Cliente e servidor** separados por uma interface bem definida.
- **Sem estado** (*stateless*): o servidor não guarda a sessão do cliente entre um pedido e outro, cada pedido leva o que precisa.
- **Cache**: as respostas indicam se podem ser guardadas e reaproveitadas.
- **Interface uniforme**: a restrição fundamental do REST.
- **Sistema em camadas**: o cliente geralmente não sabe se fala com o servidor final ou com um intermediário.
- Opcional: **código sob demanda** (o servidor manda lógica para o cliente executar).

Os recursos são identificados por endereços (URIs). Eles são conceitualmente separados das **representações** que o cliente recebe, que podem ser HTML, XML ou JSON. Um alerta: a associação dos métodos HTTP (GET, POST...) com REST é considerada uma boa prática, mas **não faz parte** do REST como Fielding o formulou originalmente.

<Brincando titulo="REST: o endereço é a coisa, o método é o verbo">

Pense numa **biblioteca**. O endereço diz **qual coisa**: "a estante de livros", "o livro número 5". O método diz **o que fazer** com ela.

Com **GET**, você só olha o livro. Com **POST**, você coloca um livro novo na estante. Com **PUT** ou **PATCH**, você troca ou corrige um livro. Com **DELETE**, você tira o livro.

Assim, "GET /livros/5" lê como uma frase: "pegue o livro 5". O mesmo endereço com outro verbo faz outra coisa.

</Brincando>

<ExemploResolvido titulo="Lendo pedidos REST">
  <Passo>`GET /produtos`: o verbo é **buscar**, a coisa é a **coleção** de produtos. Resposta: a lista.</Passo>
  <Passo>`GET /produtos/2`: **buscar** o produto de número 2.</Passo>
  <Passo>`POST /pedidos` (com dados no corpo): **criar** um pedido novo.</Passo>
  <Passo>`DELETE /pedidos/4821`: **apagar** o pedido 4821.</Passo>
</ExemploResolvido>

<Brincando titulo="Sem estado: o garçom que esquece tudo">

Imagine um garçom com **amnésia**: a cada visita à mesa, ele esquece o que aconteceu antes. Então, em cada pedido, você precisa dizer **tudo de novo**: seu nome, a mesa e o que quer.

Uma API sem estado funciona assim: cada pedido leva **todas as informações** de que o servidor precisa, e o servidor não guarda a conversa anterior.

Parece trabalhoso, mas tem uma vantagem: qualquer garçom (ou servidor) da casa pode atender qualquer pedido, porque não depende de uma lembrança guardada.

</Brincando>

<Aprofundar titulo="O que significa ser sem estado">
Numa API sem estado, o servidor **não guarda memória** do cliente entre dois pedidos. Cada pedido precisa trazer tudo o que o servidor precisa para responder (por exemplo, quem é você, quando for o caso). Isso parece trabalhoso, mas traz uma vantagem enorme: qualquer servidor de uma fileira de servidores iguais pode atender qualquer pedido, porque nenhum deles depende de lembrar do último. É assim que um site consegue crescer, adicionando servidores à fila.
</Aprofundar>

## A API como contrato: quando o cardápio muda

Uma API é uma **promessa**. O aplicativo foi escrito esperando um campo chamado "nome". Se o servidor **adiciona** um campo novo ("cor"), quem não conhece o campo novo simplesmente o ignora e nada quebra. Mas se o servidor **renomeia** "nome" para "titulo", o aplicativo procura "nome", não acha, e **quebra**. Mudanças como acrescentar parâmetros podem quebrar quem usa a API, e que recursos antigos devem ser **marcados como obsoletos** (*deprecated*) antes de saírem, para dar tempo de migrar.

<ContratoQuebrado />

<ExemploResolvido titulo="Mudança que quebra e mudança que não quebra">
  <Passo>Contrato original: a resposta tem `nome` e `preco`.</Passo>
  <Passo>Mudança A: o servidor **acrescenta** `cor`. O aplicativo continua achando `nome` e `preco`. **Não quebra.**</Passo>
  <Passo>Mudança B: o servidor **renomeia** `nome` para `titulo`. O aplicativo procura `nome` e não encontra. **Quebra.**</Passo>
  <Passo>Por isso APIs sérias avisam antes, mantêm a versão antiga por um tempo e documentam tudo.</Passo>
</ExemploResolvido>

<Aprofundar titulo="A documentação é parte da API">
Uma API precisa de **documentação**: explica quais serviços existem e como usá-los, com descrições dos pedidos, exemplos de uso, trechos de código e restrições. A documentação costuma omitir os detalhes internos e que é **difícil mantê-la atualizada**, o que leva a defeitos quando ela diz uma coisa e a API faz outra. Algumas APIs públicas dão acesso por **tokens** (chaves de acesso) ou depois de confirmar quem é o cliente. Lembre da regra de ouro da cápsula anterior: o servidor nunca deve confiar cegamente no que vem de fora.
</Aprofundar>

## Onde isso aparece no dia a dia

Quando uma página busca dados novos **depois** de carregada e atualiza só um pedaço da tela, ela usa uma chamada a uma API, quase sempre devolvendo JSON. Isso se chama requisições web assíncronas, parente do Ajax (o nome dado em 2005 a esse truque). O JSON também aparece em arquivos de configuração e em **bancos de dados**: bancos de documentos como o MongoDB guardam dados em formato parecido com JSON, e bancos como PostgreSQL e MySQL têm tipos próprios para JSON.

<Aprofundar titulo="Web API e API de biblioteca">
Existem dois grandes tipos. A **API de biblioteca** descreve o comportamento esperado de uma biblioteca de código: a biblioteca é **uma implementação** dessa especificação, e a mesma API pode ter várias implementações. A **API web** é um conjunto de especificações, em geral mensagens de pedido HTTP com respostas estruturadas em XML ou JSON, que permite que computadores ligados à internet se comuniquem. Hoje, a API web é o significado mais comum da palavra "API".
</Aprofundar>

<Resumo>

- **API**: interface para programas conversarem, como um cardápio ou contrato (o que dá para pedir e o formato da resposta).
- **JSON**: texto leve com seis tipos (objeto, lista, texto, número, booleano, nulo). Regras rígidas: aspas duplas, sem comentários, sem vírgula sobrando.
- **REST**: o endereço identifica a coisa (recurso) e o método HTTP diz a ação. Os pedidos são sem estado.
- **Códigos de status** (200, 201, 404...) acompanham cada resposta.
- **Mudar a API** pode quebrar quem a usa: acrescentar costuma ser seguro, renomear não.
- **Documentação** é parte da API, e é difícil de manter em dia.

**Um pouco de história.** Wilkes e Wheeler organizaram uma biblioteca de sub-rotinas para o EDSAC nos anos 1940. A expressão "application program interface" apareceu em 1968. Roy Fielding descreveu o REST em 2000, a primeira mensagem JSON foi enviada em abril de 2001, o ECMA-404 saiu em 2013 e a RFC 8259 em 2017.

</Resumo>
